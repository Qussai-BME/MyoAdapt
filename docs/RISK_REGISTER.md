# MyoAdapt Research Release Risk Register

This register records risks identified during the pre-release engineering review. It is not an ISO 14971 risk-management file and does not establish clinical acceptability. Risk ratings describe the research-software release context only.

| ID | Domain | Risk statement | Pre-release control in this package | Residual risk | Required owner action |
|---|---|---|---|---|---|
| R-001 | Intended use | A user may mistake research outputs for clinical, diagnostic, therapeutic, or autonomous-control recommendations. | Research-only notices are placed in README and API metadata/root page. | High outside controlled research. | Product owner must keep the notice prominent in every hosted interface and marketing surface. |
| R-002 | Input validity | Malformed, non-finite, ragged, or excessive REST payloads may consume resources or create undefined model behavior. | REST payload checks enforce finite values, rectangular batches, feature limits, and batch limits. | Medium because network rate and body limits are external. | Gateway operator must set request-size limits, rate limits, and alerting. |
| R-003 | Authentication | A public endpoint might be started without a shared secret. | `MYOADAPT_REQUIRE_API_KEY=true` makes a missing key fail startup; Compose enables it by default. | Medium; an API key is not user identity or authorization. | Use an identity-aware TLS gateway, rotate secrets, and restrict network access. |
| R-004 | Streaming isolation | One WebSocket client might affect another client or submit oversized samples. | Per-connection inference engines plus bounded message/sample/channel checks and optional API key. | Medium; network DoS and connection quotas are not solved in-process. | Enforce connection limits and rate controls at the reverse proxy. |
| R-005 | Error disclosure | Internal paths, model details, or exceptions could be returned to clients. | API handlers log detailed errors server-side and return constrained messages. | Low to medium depending on logging configuration. | Protect logs, redact identifiers, and monitor error volume. |
| R-006 | Model deserialization | Loading a malicious pickle or unrestricted PyTorch artifact can execute code. | Classical load supports a trusted external SHA-256 requirement; synthetic loaders use `weights_only=True`. | High if an attacker controls a pickle and expected hash or the deployment filesystem. | Treat pickle as trusted-only; use immutable, reviewed artifact storage and independent provenance. |
| R-007 | Artifact integrity | A local sidecar hash could be altered with a model artifact. | Code can compare to `MYOADAPT_MODEL_SHA256` from deployment configuration. | Medium; hash comparison is not signature/provenance. | Publish checksum via a protected release channel; add signed provenance in CI. |
| R-008 | Dependencies | Transitive packages may contain disclosed vulnerabilities. | `cryptography>=50.0.0` floor added for `PYSEC-2026-3552`; dependency audit documented. | Medium because dependency graphs change. | Run `pip-audit` and container scanning for each release. |
| R-009 | Container privilege | Root runtime and broad host exposure may amplify compromise. | Non-root Dockerfile; Compose binds to loopback, drops capabilities, sets no-new-privileges, read-only root, tmpfs, and PID limits. | Medium; image, host, and reverse proxy still require maintenance. | Build and scan images in CI; keep base images patched; restrict mounts. |
| R-010 | Data privacy | EMG, identifiers, predictions, and logs may be personal data and may require heightened protection. | Documentation provides an operator checklist and avoids universal classification claims. | High when processing real participant/patient data. | Controller must determine lawful basis, notices, retention, access control, security, transfers, and DPIA need. |
| R-011 | Dataset licensing | Public datasets may have conditions incompatible with a planned distribution or use. | Documentation requires dataset-specific license/consent review. | High if ignored. | Data steward must confirm permissions, attribution, and participant/IRB restrictions. |
| R-012 | Generalization | Reported performance may not transfer across users, sessions, sensors, electrode placements, tasks, or populations. | Evaluation utilities exist; public wording now requires protocol-specific evidence. | High without target-context validation. | Research lead must produce representative held-out, cross-session, and cross-device evidence. |
| R-013 | Calibration | Order-based or non-independent calibration may look better than operational calibration. | Documentation labels calibration tooling experimental and requires protocol-specific validation. | High for clinical/safety-critical claims. | Use predeclared subject/session/time holdouts and report calibration error and coverage. |
| R-014 | Synthetic fallback | Synthetic data can be mistaken for real-data validation. | Release documentation requires explicit labeling and prohibits performance claims from synthetic runs. | Medium. | Disable fallback in formal experiments or make every output carry the synthetic-data marker. |
| R-015 | Human oversight | Confidence/trust displays may be mistaken for an enforced safety mechanism. | Documentation calls them informational, not safety controls. | High in autonomous or clinical use. | Design and validate independent human-in-the-loop and fail-safe controls in the target system. |
| R-016 | Reproducibility | Unsigned manifests and environment hashes can be mistaken for a certified or deterministic record. | Documentation corrects terminology and requires independent release evidence. | Medium. | Use locked environments, immutable tags, signed provenance, and rerun protocols. |

## Review cadence

Review this register at every release, after a dependency/security advisory, after any change to intended use, model architecture, data source, data retention, external interface, or deployment environment, and before any claim involving users outside the documented research context.
